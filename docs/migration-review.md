# 저장소 통합 1차 검토

이 변경은 백업·대조 도구와 저장소 전환 준비입니다. 현재 앱의 저장소는 전환하지 않았으며 SQL 초안도 실행하지 않았습니다.

## 확인 결과 (2026-09-09)

- Apps Script 목록 35개: 저장 내용 33개, 내용 없음 2개.
- Supabase 프로젝트 33개. 개수가 비슷해도 같은 프로젝트 집합은 아닙니다.
- ID 연결 4개, 정확한 이름만 일치 8개, 연결 없음 20개, 동일 대상 중복 2개, 내용 없음 1개로 분류했습니다. 내용 없는 프로젝트 중 하나는 중복 분류에 포함됩니다.
- 저장 내용 32개는 일정 중심 형식입니다. 객실·발주 품목이 있는 저장 내용은 1개이며 객실 유형 2개, 품목 2개입니다. 이것만으로 모든 기존 발주 데이터가 백업되었다고 판단할 수 없습니다.
- API 백업은 목록에 있는 키만 읽습니다. 목록에서 빠진 키는 소유자용 `apps-script/export-properties.gs`로 별도 확인할 수 있습니다. 백업은 일괄 트랜잭션이 아니므로 실제 전환 전 저장을 잠시 멈추고 재추출해야 합니다.
- 실제 프로젝트명과 원본 데이터는 공개 저장소에 포함하지 않습니다.

## 포함된 수정

`orderItemsApi.js`는 업체 ID, 규격, 단위, 브랜드, 비고를 왕복 보존합니다. 객실 연결이 없는 품목은 기존 행을 삭제하기 전에 오류로 중단합니다. 기존 DELETE 후 INSERT 방식 자체는 아직 남아 있습니다.

새 document adapter와 SQL 초안은 전체 JSON 보존, 버전 충돌 감지, 이전 버전 이력을 제안합니다. 앱에 연결하지 않았습니다. SQL 실행 테스트와 권한 설정도 아직 수행하지 않았습니다.

## 실행

```sh
node scripts/export-legacy.mjs /private/path/legacy-backup.json
node scripts/audit-legacy.mjs /private/path/legacy-backup.json /private/path/audit.json
node --test tests/*.test.mjs
npm run build
```

스크립트는 조회만 수행하며 백업 파일을 덮어쓰지 않습니다. 캘린더 동기화나 이메일 발송을 호출하지 않습니다.

## 다음 적용 순서

1. 연결 없음·이름 일치·중복 대상을 검토해 명시적 ID 매핑을 확정합니다. 기존 원본은 모두 보관합니다.
2. 별도 테스트 환경에서 SQL, 권한, 최초 import 및 건수/JSON 동일성을 검증합니다. 프로젝트 이름·예산·일정과 기존 정규화 테이블의 갱신 책임도 정해야 합니다.
3. 모든 저장 경로를 한 저장소로 전환하고 두 브라우저의 동시 저장·복구를 검증한 뒤 전환합니다.
4. 담당자 작성 → 팀장 검토·확정 → 엑셀 다운로드 → PDF 변환 → 수동 업체 전달 흐름을 구현합니다. 다운로드와 전달 완료는 구분하고 확정 후 수정은 재검토합니다.
5. 발주서는 확정 당시 단가·수량·업체를 보존합니다. 현재 order_items.quantity는 객실당 수량을 저장하므로 최종 발주 수량으로 그대로 사용하면 안 됩니다. 객실수·층 배치·포장단위 계산과 기존 발주서 양식 이식이 필요합니다.

## 검증

Node 테스트 7개 통과, Vite 프로덕션 빌드 통과. 번들 크기 경고는 남아 있습니다. 실제 DB 쓰기, 캘린더 실행, 배포는 수행하지 않았습니다.
